# Project Rules: Local-First PBS Workflow

Read this file before inspecting, changing, or running project code.

- The local checkout is authoritative. Use `LOCAL_CONDA_ENV` for lightweight local tests; use the configured SSH host, `REMOTE_CONDA_ENV`, and PBS queue for substantial GPU and long jobs. Never train on a login node.
- Read this project's `.workflow/config.env` before every operation: it is executable trusted shell and the sole configuration source. Reuse its existing binding automatically; never copy project settings back into the global skill template. Fill missing host, absolute base directory, stable `PROJECT_SLUG`, and environment/queue settings from existing configuration or user input. Verify `REMOTE_HOST:REMOTE_BASE_DIR/PROJECT_SLUG` and avoid accidental remote-directory sharing. If required values are missing, report that binding is pending. Confirm queue resource and walltime limits; template values are examples. Store no secrets here.
- Prefer the project's `scripts/remote-workflow`; without a project argument it uses its own project root, regardless of the current directory. Select only the requested operation: `doctor`, `sync`, `submit`, `status`, `pull`, `github-check`, or `github-stage`. `submit` always syncs again. Initialize new projects from the full skill package with an explicit target; review their sync/retrieval lists. Initialization/binding alone does not authorize transfers, submission, background watchers, or recurring sync.
- `init` saves a stable slug for a new configuration and preserves existing files; repeating it does not rebind or upgrade. Local folder moves/renames preserve the saved remote binding. Copies intended as new projects require a new explicit slug/destination and review of copied checkpoints and `DONE_FILE` before running.
- Before submission: inspect code/configuration/output paths, perform local checks, and preview transfers. For a requested full experiment, submit one PBS job that runs smoke and validates it, then immediately starts the full run in the same allocation without another submission or approval. Stop if smoke/validation fails; honor smoke-only requests. Point `TRAIN_COMMAND` at a project wrapper that exits on failure and `exec`s the resumable full entrypoint; do not use `smoke && full` directly in this value. Keep smoke outputs/checkpoints separate and never let smoke write the full run's `DONE_FILE`.
- Budget resources for the full run and time for both stages plus validation/checkpoint cleanup. Use `MAX_CONTINUATIONS=0` when the run fits one slice; explicitly enable a finite continuation chain for longer work. Continuations resume the same full experiment and skip passed smoke only when its code/configuration still matches. An explicit one-job cap takes precedence and requires checking that the requested work fits before submitting.
- Before every Agent-performed transfer, inspect the complete dry-run list and per-file bytes. Never transfer a file >= 10 MiB (10,485,760 bytes) as an Agent: provide the user an exact command with source/destination/size and verification instead. Use resumable downloads. Smaller required files can transfer automatically to known destinations; report and verify them. CLI execution itself does not enforce this Agent-only threshold.
- Preserve `.workflow/sync-exclude.txt` protections, inspect deletion effects, and exclude any additional private data. Code moves through SSH/rsync. `.workflow/important-results.txt` selects results to retain locally.
- For queued/waiting jobs or expected runtimes above five minutes, stop polling and hand off: give exact job ID, remote/log/checkpoint/result/completion paths, and resolved queue/log/artifact commands. A missing `qstat` entry does not prove success.
- Work exceeding one slice uses the supplied `afterany` chain. Save atomic checkpoints each epoch and on SIGTERM/SIGINT; include model, optimizer, scheduler/scaler, epoch/step, RNG, and essential trainer/sampler state. Resume the next unfinished step automatically. After fatal deterministic errors, verify that continuation stopped: the script's `qdel` cancellation is best-effort. Inspect queue and logs; some setup failures do not write `TRAINING_FAILED`.
- Write the configured `DONE_FILE` only after training and required result validation succeed. Check logs, checkpoints, results, and marker together. Do not discard an existing checkpoint or marker without understanding it.
- Use `configs/`, `src/`, `scripts/`, `tests/`, `pbs/`, and `docs/` for their usual purposes. Experiment artifacts go in `outputs/{checkpoints,logs,results,reports,figures,status}/`; paper figures and generation scripts go in `results/`; temporary files go in `tmp/`.
- `data/raw/` is immutable. Keep one canonical result, preferably readable JSON. Overwrite derived results unless preservation is requested; inventory/classify files before deleting or reorganizing them.
- GitHub is optional. Only publish when requested or already established. Run `github-check`, inspect whitelist/staged content, and apply the separate 99 MiB guard and the 10 MiB Agent transfer rule. Never commit credentials, keys, `.env`, private/raw data, or files >= 100 MiB. Do not create repositories or force-push without explicit authorization.
- Report exact commands, output paths, job IDs, and completion evidence; derive project roots and keep scripts portable with `set -euo pipefail` where appropriate.

## Unified HPC task status

These requirements apply when submitting or maintaining PBS tasks and their status integration. They do not authorize a new experiment, watcher, remote transfer, or scheduling change.

- Register every main task, continuation, CPU controller, queue watcher, and compatibility-parked job with the project's status view. Keep machine-specific host/root settings in `.workflow/config.env`, task definitions in `configs/`, and atomic submission/relationship receipts in `outputs/status/`. Reuse compatible existing manifests and relay state rather than creating duplicate authoritative records. An aggregate dashboard reads project records; it must not become the source of remote bindings.
- Record a stable project/task identity, experiment identity (including model/dataset/variant/seed as applicable), display label, remote absolute project root, job role, full PBS job ID, parent/controller/task relationships, and log/checkpoint/result/completion paths. Keep unsubmitted IDs and inapplicable paths null. Continuations and retries of the same experiment retain their logical identity; distinct experiments must not be merged. Update receipts after every submission or replacement.
- Match jobs using explicit receipts, PBS environment metadata, and recorded relationships first; work directory and submit-script paths are supporting evidence. Do not hard-code numeric job IDs, rely only on truncated PBS names, or infer a parent/child relation from similar names or simultaneous submission. Preserve genuinely unmatched jobs for inspection.
- Display one logical computing task across its active job and successors. Separate main/continuation roles from CPU controller/watcher/parked roles. Count running computing tasks independently from running control jobs; a CPU training task is still a computing task, while a CPU watcher running does not mean GPU computation is running. Attach a dedicated controller only with explicit evidence; display a shared watcher in a separate control section.
- The default view shows task label, actual PBS queue, current main job ID, running/queued/waiting-for-continuation/stopped-or-failed/completed status, and latest relevant progress. Show missing progress as unavailable, not as failure. Unknown jobs must show ID, name, queue, PBS state, and working directory rather than IDs alone.
- `--details` shows all related IDs, PBS states, roles and recorded relationships, plus resolved absolute log/checkpoint/result/completion paths. `--json` carries the same identities and classification. Default, detailed, and JSON views must agree and must not double-count a controller or successor.
- Determine status from PBS plus logs belonging to the current experiment/attempt and validated artifacts. Do not let stale failure logs or old completion markers override a replacement run. Completion requires the configured marker and expected valid results; absence from the queue alone never proves success. Report duplicate active computing jobs and uncertainty explicitly.
- Keep status queries read-only: they must not submit/retry/move/delete jobs, release holds, change priority/resources, modify configuration, or start persistent monitors. Job management requires separate user authorization. Do not repeatedly poll long-running/queued jobs; hand off exact status/log/artifact commands.
- When adding a task or changing its continuation/control mechanism, verify that main jobs, successors and control jobs appear in the intended groups and that default/`--details`/`--json` agree. An authorized submission must remain recorded even if display integration fails; report the missing integration and fix it within scope instead of blindly submitting a duplicate. Document whether integration is implemented and checked; updating these rules alone does not implement a dashboard.

## GPU selection after allocation

- For GPU runs, choose the device after entering the PBS compute allocation and before initializing CUDA or loading models. Recheck on each new allocation, continuation, and fresh retry process; do not hard-code GPU 0 or reuse a previous node's GPU index.
- Consider only GPUs assigned and accessible to this job. Preserve PBS/cgroup restrictions and the existing `CUDA_VISIBLE_DEVICES` boundary; an idle GPU elsewhere on the node is not a candidate merely because `nvidia-smi` lists it. If the assignment is unclear, report it rather than widening visibility.
- Query the eligible GPUs' free memory and utilization (for example with `nvidia-smi`). Select the GPU with the most free memory, breaking ties by lower GPU utilization, then stable UUID order. For a requested multi-GPU run, select the required number using the same ordering without changing its world size; with only one eligible GPU, use that GPU. If the query or device mapping fails, stop with a clear diagnostic instead of silently falling back to GPU 0.
- Resolve physical index/UUID against CUDA-visible logical indices before binding the training process; use a supported UUID or an explicitly verified mapping. Set visibility/device selection before CUDA initialization. After restricting a single selected GPU, the application uses logical `cuda:0`, which need not be physical GPU 0. Keep the selection fixed while that process runs.
- Record the PBS job ID, hostname, original `CUDA_VISIBLE_DEVICES`, eligible/visible GPU counts, each eligible GPU's index/UUID, free/total memory and utilization, and the selected GPU(s) in the current job log. Implement and verify this selection in the PBS/project launch entrypoint when preparing a GPU run; documentation alone does not change existing launchers or running jobs.
